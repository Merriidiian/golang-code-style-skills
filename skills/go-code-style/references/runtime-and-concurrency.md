# Контексты, жизненный цикл и конкурентность

## Контекст операции и процесса

Контекст запроса принадлежит запросу; контекст фонового relay — его жизненному циклу. Фоновая доставка уже зафиксированного Outbox не должна зависеть от того, дождался ли HTTP-клиент ответа.

- Передавай контекст до SQL- и сетевого вызова. Вызывай `cancel`, возвращённый `WithCancel`/`WithTimeout`, у владельца контекста.
- Контекст ребёнка не продлевает родительский deadline. Планируй оставшийся бюджет с учётом декодирования, записи результата и остальных зависимостей.
- Отмена кооперативна: закрытый `Done()` не означает, что горутина завершилась. Нужны наблюдение отмены и отдельное ожидание окончания.
- Храни в context только данные области запроса, уместные по контракту. Зависимости сервиса и обязательные бизнес-параметры передавай явно. Идентификатор арендатора из context допустим лишь после проверки доверенной границы.
- Если задача должна пережить запрос, определи её владельца и устойчивый приём. Простое `go work(context.Background())` не обеспечивает сохранность работы.

## Сборка и остановка

Пусть `main` вызывает функцию `run`, которая возвращает ошибку после выполнения нужной очистки. `os.Exit` не выполняет отложенные вызовы, поэтому не используй его внутри рабочего кода, рассчитывающего на `defer`.

При остановке определи зависимости фаз, а не универсальный порядок всех сервисов:

1. Прекрати приём новой работы, снизь readiness; учти время распространения маршрутизации.
2. Дай принятым запросам и работникам согласованную возможность завершиться или отмениться.
3. Дождись управляемых горутин с ограниченным бюджетом.
4. Закрой БД, брокер и другие ресурсы после завершения их пользователей.

Не отменяй автоматически все активные запросы сигналом процесса, если выбранная политика предусматривает их осушение. Для `Server.Shutdown` создай новый ограниченный контекст: контекст сигнала к этому моменту уже отменён.

`Shutdown` закрывает слушатели и ожидает обычные активные соединения. Истечение его deadline возвращает ошибку и само по себе не закрывает все активные соединения. Политику принудительного `Close`, WebSocket/hijacked-соединений и фоновых задач задай отдельно. Внешний grace period должен покрывать все последовательные фазы, включая `preStop`.

Liveness проверяет необходимость восстановления процесса; readiness — возможность принимать выбранный класс работы. Отказ необязательной зависимости не должен автоматически запускать цикл перезапусков. Локальное `ready=false` не является запретом для всех бизнес-обработчиков и не мгновенно обновляет балансировщик.

## HTTP и синхронные клиенты

- Настрой пределы заголовков, тела, времени чтения, ожидания соединения и выполнения операции под конкретный endpoint. `MaxBytesReader` ограничивает размер, но не скорость передачи тела.
- Deadline контекста не устанавливает автоматически сетевой deadline чтения `r.Body`. Используй подходящие транспортные ограничения; для streaming учитывай длительные законные ответы.
- Повторно используй клиент и transport. Закрывай response body по контракту клиента; чтение/освобождение тела учитывай для повторного использования соединений.
- Ограничивай число попыток и общий deadline. Повтор изменяющей команды допустим при определённой идемпотентности. Таймаут после отправки означает неизвестный исход, а не доказанный откат.
- Не повторяй ошибки валидации или бизнес-отказы как временные сетевые сбои. Учитывай `Retry-After`, backoff с jitter и совокупную нагрузку от повторов на нескольких слоях.

## Горутины и ограничение ресурсов

Для запускаемой горутины должны быть понятны создатель, источник работы, сигнал остановки, получатель ошибки и тот, кто ждёт завершения.

- Ограничь число обработчиков, размер очереди, буферы брокера и ожидание пула. Размеры выбери по нагрузке и стоимости операции, а не по фиксированному множителю числа CPU.
- Для заполненной очереди выбери поведение: ждать до deadline, отказать, сбросить допустимую работу или сохранить её устойчиво. Задокументируй внешнюю семантику, например `429`/`503`, если это HTTP API.
- Mutex подходит для защиты общего состояния; канал — для передачи владения и координации. Не подменяй простой mutex сложным конвейером без пользы.
- Отправка и получение в блокирующем цикле должны иметь путь отмены. Закрытие канала принадлежит стороне, которая знает, что отправителей больше нет; координируй несколько отправителей.
- Не держи mutex во время длительного I/O, если это не намеренный и обоснованный контракт. Не вызывай callback под блокировкой без анализа повторного входа.
- `WaitGroup` отслеживает завершение, но сам не передаёт ошибки и не отменяет работу. Используй уже принятый в проекте механизм координации, не добавляя зависимость автоматически.

## Производительность и наблюдаемость

Сначала воспроизведи проблему и измерь CPU, аллокации, ожидания и contention подходящим профилем. `-race` находит некоторые гонки, но не доказывает отсутствие deadlock, потери сообщения или нарушения инварианта.

Структурированный журнал должен связывать операцию, ошибку и допустимые correlation-поля. Не логируй секреты и полные тела по умолчанию. Метки метрик ограничивай по cardinality: ID запроса и пользователя не подходят для обычных labels. Возврат обработчика и получение полного ответа клиентом — разные события.

Основы: ПКП-1, ПКП-3, ПКП-4, ПКП-7; уточнение семантики `context` и `net/http` — по стандартной библиотеке.
