# Проверки и ревью Go

## Подбор проверок

Сначала выполни необходимые проектные команды. Следующие команды — варианты для подходящего проекта, а не требование запускать всё при каждой правке:

```sh
gofmt -w path/to/changed.go
go test ./internal/order/...
go test ./...
go vet ./...
go test -race ./...
```

Для `go.work`, build tags, CGO и отдельных модулей выбери соответствующую рабочую директорию и флаги. Не обновляй `go.mod`/`go.sum`, toolchain и зависимости без необходимости. Для недоступного инструмента сообщи ограничение, не заявляя об успешной проверке.

## Поведение, которое стоит проверять

- Табличные тесты подходят наборам входов и переходов состояния. Называй случаи по проверяемому правилу.
- Бизнес-инвариант проверяй через каждый затронутый вход, если есть риск различий HTTP/worker/import. Само правило должно иметь быстрый тест без инфраструктуры.
- Ошибки проверяй через категории и поля, а не точный текст, если текст не является контрактом.
- Конкурентные сценарии синхронизируй каналом, барьером или управляемой точкой сбоя. `time.Sleep` для «попадания в гонку» делает тест случайным.
- Для deadline проверь завершение операции и освобождение ресурсов с разумным запасом времени. Не требуй точного совпадения с миллисекундой.
- Отдельно проверь отмену во время ожидания очереди, заполненную очередь и завершение фонового обработчика.
- Логику адаптера можно проверять `httptest` или подставной зависимостью. Особенности SQL, блокировок и RLS требуют реального PostgreSQL в изолированном окружении.
- Не заменяй все зависимости mock-объектами с проверкой порядка внутренних вызовов: такой тест может закрепить реализацию и пропустить неверный результат.

## Benchmark

Измеряй одну понятную операцию при фиксированных условиях. Запиши версию Go, данные, конкурентность, ресурсы и долю инфраструктурной работы. Сравнивай одинаковую семантику; benchmark координации очереди не измеряет реальную пропускную способность сервиса с БД.

Профилируй до усложнения кода. После оптимизации проверь одновременно корректность, нужную метрику и расход памяти; ускорение среднего времени может ухудшить хвост задержек.

## Ревью

Приоритет имеют нарушения поведения и контрактов: потерянная причина ошибки, неограниченная горутина, сломанный deadline, публичный тип с изменённой семантикой, утечка зависимости или ресурса. Форматирование и предпочтения указывай отдельно и только если они значимы для проекта.

Полезная находка содержит конкретное место, воспроизводимое условие и наблюдаемый эффект. Предложение «разнести всё по слоям» без проблемы и цены изменения не является достаточным обоснованием.

Основы: ПКП-2–4, ПКП-7 и примеры `orderflow-cqrs`.
