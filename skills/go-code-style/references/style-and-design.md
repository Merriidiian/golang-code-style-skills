# Имена, пакеты, типы и ошибки

## Имена и форматирование

- Используй `MixedCaps`/`mixedCaps`, без подчёркиваний в обычных Go-идентификаторах. Соглашения JSON, SQL, generated-кода и существующих внешних контрактов рассматривай отдельно.
- Сохраняй аббревиатуры: `userID`, `HTTPClient`, `parseURL`. Имя экспортируемого элемента должно читаться вместе с пакетом: `order.Service`, без повторного `order.OrderService`, если повтор ничего не уточняет.
- Пакет называй по ответственности. `utils`, `common`, `helpers` часто скрывают несвязанные обязанности; перемещай код только когда это помогает текущей задаче.
- Receiver обозначай коротко и одинаково у методов одного типа: `s *Service`, `c *Client`. `this` и `self` скрывают смысл обычного параметра Go.
- Короткие имена подходят маленькой области видимости; на границах и в больших функциях называй роль: `requestHash`, `shutdownTimeout`.
- Пиши комментарии к экспортируемым контрактам, сложным инвариантам и причинам решения. Комментарий должен объяснять смысл, ограничения или владение, а не пересказывать строку кода.
- Не вводи произвольные лимиты длины функции и не разбивай связный алгоритм ради числа строк. Ранние возвраты помогают оставить основной путь без глубокой вложенности.

## Пакеты и зависимости

Выбирай границы по поведению и направлению зависимостей. Возможная структура сервиса:

```text
cmd/server/             сборка приложения и завершение
internal/order/         состояние и правила заказа
internal/command/       сценарий выполнения команды и его порты
internal/commandhttp/   входной HTTP-адаптер
internal/commandpg/     SQL-адаптер
```

Это пример, а не требуемое дерево. Для небольшого инструмента достаточно меньшего числа пакетов. Для существующего проекта сначала сохраняй его понятные соглашения.

Предметная модель не должна зависеть от `net/http`, `pgx` или Kafka-клиента, если её задача — выразить независимые бизнес-правила. DTO запроса, доменный объект, запись БД и конверт события имеют разные обязанности; разделяй их при различии контрактов, а не механически для каждого типа.

Интерфейс определяет пакет, которому нужна возможность:

```go
type OrderReader interface {
    ByID(ctx context.Context, id string) (Order, error)
}

func NewService(reader OrderReader) *Service {
    return &Service{reader: reader}
}
```

Не экспортируй внутренние подробности «на будущее». Универсальный repository, service locator и собственный DI-фреймворк требуют конкретной причины. Дженерики полезны для действительно общего алгоритма, но не заменяют моделирование предметных различий.

## Типы и владение

- Делай нулевое значение полезным, когда это естественно. Когда объект без проверки недопустим, дай конструктору явный контракт и проверь инварианты.
- Выбирай pointer receiver при изменении состояния, наличии `sync.Mutex`, дорогом копировании или необходимости общей идентичности. Маленькое независимое значение можно передавать по значению. Не копируй использованные примитивы синхронизации.
- Учитывай aliasing срезов, map и указателей. Если вызывающий не должен менять внутреннее состояние агрегата, возвращай независимую копию или узкий доступ.
- Не используй `any`, reflection и type assertion там, где обычный тип выражает контракт. Проверяй assertion, если неверный тип возможен на входе.
- Для точных денежных величин выбирай целые минимальные единицы или подходящий decimal-контракт; проверяй переполнение при арифметике. Это решение предметной области, а не требование ко всем числам.
- Не задавай правило «всегда возвращать nil/пустой срез»: учти JSON-контракт и соседний код. Не меняй `null` на `[]` случайно.

## Ошибки

```go
var ErrNotFound = errors.New("order not found")

func (s *Service) Find(ctx context.Context, id string) (Order, error) {
    order, err := s.reader.ByID(ctx, id)
    if err != nil {
        return Order{}, fmt.Errorf("find order %s: %w", id, err)
    }
    return order, nil
}
```

Пример показывает сохранение причины; конкретный формат сообщения и допустимость ID в диагностике определяет проект.

- Sentinel подходит устойчивой категории; типизированная ошибка — когда вызывающему нужны поля, например текущая и требуемая версии. Не сравнивай тексты ошибок для управления потоком.
- `%w` делает причину доступной вызывающему. Оборачивай осмысленно: не превращай случайную ошибку драйвера в обещание публичного API, если адаптер должен преобразовать её в свой контракт.
- Добавляй новый контекст там, где он помогает расследованию; не повторяй один и тот же текст на каждом уровне. По возможности логируй сбой на границе, которая принимает окончательное решение.
- Не игнорируй ошибки `Commit`, `Scan`, `rows.Err`, записи ответа и закрытия значимого выходного ресурса. Ошибку `Rollback` после уже завершённой транзакции обычно обрабатывает принятая обёртка.
- `panic` не является обычным результатом валидации, таймаута или отсутствия записи. Восстановление на границе не должно превращать сбой в успешный ответ.
- Не выдавай наружу необработанные SQL-ошибки, секреты и внутренние детали; сохраняй диагностику в допустимом внутреннем канале.

Основы: ПКП-2, ПКП-7 и официальные Go Code Review Comments. Происхождение и уточнения — в [sources.md](sources.md).
